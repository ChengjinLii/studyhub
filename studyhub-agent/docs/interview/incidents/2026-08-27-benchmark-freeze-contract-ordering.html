残余风险

Git 是恢复锚点

首次构建且尚无冻结提交时，脚本最终仍会使用 HEAD；这时必须明确这是新 Benchmark，而不是旧版本复现。

原子发布仍可加强

当前通过顺序和 Git fallback 抵御中断。更强方案是先在临时目录完成全门，再原子替换公开冻结资产。

60 秒回答我在重跑 Benchmark v2 完整质量门时遇到一个顺序 Bug。Builder 会先生成 candidate manifest，但新增的 9B Base calibration test 要求 manifest 已冻结，因此在 finalize 前必然失败。中断后 candidate manifest 又没有 builder commit，重试时脚本回退到当前 HEAD，生成了不同 hash。我的修复没有放宽合同，也没有改证据 hash，而是把冻结绑定测试放到 finalize 和两层 validator 之后，并让中断恢复从 Git 读取最后一个冻结 builder。完整重跑后 manifest 恢复到原 da804…，两份 9B 证据绑定通过，challenge 21/21。
3 分钟追问这个问题说明可复现 Benchmark 不只是固定 seed，还要固定发布状态机。预冻结阶段应该验证任务、grader、负对照和源码；证据绑定只能在冻结资产产生后验证。原流水线把两类断言混在同一个 pytest 阶段，导致正确断言在错误时机执行。更危险的是中断后的 retry：如果只看 worktree manifest，它已经是 candidate，脚本就失去原 builder 锚点并采用 HEAD。我先根据 diff 排除任务内容漂移和证据写错，确认变化集中在时间、builder 与派生 hash；随后拆分阶段、增加 Git fallback，并显式用原 builder 完整复跑。最终不是“让测试绿”，而是恢复相同 manifest hash。残余风险是发布还不是临时目录原子替换，后续可以进一步强化。
