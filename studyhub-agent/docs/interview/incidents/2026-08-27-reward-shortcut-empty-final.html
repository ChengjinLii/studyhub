B_CONTROLLED_PROJECT · REWARD REGRESSION · NOT A NATURAL INCIDENT

Correct Tool Call,
Empty Final Answer

一个函数调用可以完全正确，但模型不向用户给出最终答案。若 Reward 只看 Call，它会把“做到一半”当成高质量策略。

1.0FUNCTION CALL QUALITY
-1.0EMPTY ANSWER QUALITY
0.4FIXED TASK SUCCESS
≤ 0FINAL TOTAL CONTRACT
真实性声明：这是隔离单元测试中的受控漏洞样例，用于验证 Reward 可利用面；没有声称正式 Pilot 中模型曾大规模利用该 shortcut。
30 秒结论。旧 Function Calling 分支计算了 answer score，却没有把它用于 task success；正确 call、空 Final 仍可能获得约 0.8。修复后 function task success 使用 70% call + 30% answer，空 Final 触发违规与非正总分，并由独立 strict evaluator 再检查 nonempty final。

漏洞结构

旧行为

Call 正确 → function score=1
Evidence/citation 固定为 1
空 Final 只做较小软扣分

R ≈ 0.4 + 0.25 + 0.15 + 0.15 − 0.15 = 0.80
→

修复后

Call 与 Answer 共同决定 task success
empty_final_answer 进入 violations
总分被封顶到非正

R_task = 0.70 R_call + 0.30 R_answer
empty final ⇒ total ≤ 0

为什么属于 Reward hacking 风险

设计意图可被优化的代理目标风险
完成工具任务并向用户回答只把隐藏 expected call 调对模型学会提前停止
使用 Observation 形成结论调用工具后不消费结果离线 call metric 好看，实际无用

60 秒回答Reward hacking 不一定是模型输出奇怪字符，更常见的是它找到组合权重的捷径。这例中工具调用是局部正确，但用户任务没有闭环。修复不能只加一个小 penalty，而要把 Final 纳入 task success，并用 hard contract 和独立 strict evaluator 双重约束。
3 分钟追问继续展开可讲 component weight calibration、为何 hard gate 只用于不可接受行为、parser FP/FN、counterfactual test、Reward 上升但 holdout 下降的监控，以及为什么该案例只能标 B，不能说是自然训练事故。
边界：本案例证明代码层 shortcut 已被封住，不证明 Reward v2 没有其他可利用面。正式训练仍需持续检查 Reward、strict success、family slice 与代表轨迹是否一致。
