为什么是 Agent？训练链路怎样拆分？

A · 真实链路

StudyHub 需要模型在不完整信息下自主决定是否搜索、如何改写 query、读取哪个证据、是否继续以及何时停止；这比一次固定 RAG 调用多了环境状态和行动反馈。Hermes 负责工具循环，SGLang 服务当前策略，Frozen Environment 执行任务级工具，Reward v2 用隐藏 verifier 打分，AReaL 完成 GRPO 与 LoRA 更新。

AReaL Task → StudyHubHermesWorkflow → Hermes AIAgent
      → SGLang / Qwen3.5 Policy → Tool Call
      → FrozenTaskEnvironment → Observation → Final Answer
      → Hidden Verifier / Reward v2 → GRPO LoRA Update

Hermes

消息状态、工具循环、停止条件、重复失败与 no-progress guardrail；不负责 optimizer。

StudyHub Runtime

安装冻结 prompt、注册任务工具、隔离宿主能力、落 Reward 和轨迹证据；不重写 Hermes 核心。

AReaL + SGLang

前者组织 rollout/logprob/advantage/update，后者做高吞吐推理和 LoRA hot load。

追问：Agentic RL 与普通 reasoning RL 有何区别？
reasoning RL 常在单次文本生成后由答案 verifier 打分；Agentic RL 的轨迹包含状态、动作、工具 observation、错误恢复和停止决策。Reward 既评价 outcome，也要约束调用、证据、引用和权限。长轨迹还带来 credit assignment、环境确定性和 policy staleness 问题。
追问：为什么不在 AReaL 里手写 loop？
保留 Hermes 能复用既有工具 schema、消息回放、停止和 guardrail 语义，避免生产 Agent 与训练 harness 演化成两套不一致的行为协议。StudyHub 只在训练边界做最小配置。
代码： training/rl/hermes_workflow.py、training/rl/frozen_environment.py、training/rl/open_agent_driver.py。网站 backend/、frontend/、数据库、OSS 与支付不在 rollout 可达边界。

同一批开放数据，SFT 与 RL 为什么不能同样使用？

A · 数据审计

SFT 看专家示范；RL 只拿任务、工具和冻结环境，让策略自己 rollout。Gold answer、gold tool sequence 和 gold evidence 从 policy context 隐藏，只进入 verifier。具体样本再按 source/group lineage 隔离，避免“同来源体系”变成“同样本泄漏”。

不可变来源

记录 repository/dataset、revision、license、raw hash、adapter commit 和过滤前后数量。

Lineage Split

压缩包提醒：数据何时算“够”？
不是达到某个条数就算够。要同时看 coverage cell、模板/近重复、learning curve、per-source retention、mixed/all-fail/all-success group、有效 action token、rollout 成本和新增数据的边际收益。当前 3,000 条 SFT 与 2,400 条 RL 是受控实验规模，不代表覆盖真实 StudyHub 用户分布。
当前事实： SFT 共 3,000 条；RL v2 为 2,000 train / 400 validation，公开 Oracle 字段为空，SFT/RL lineage overlap 为 0，train/validation group overlap 为 0。依据： datasets/processed/*/manifest.json、scripts/data/audit_open_rl_tasks.py、training/rl/budget_contract.py。

SFT 学什么？训练到什么程度才进入 RL？

A · 配方与数据结果进行中

SFT 先提供稳定的行为先验：聊天模板、Tool Call JSON、给定证据下的多跳推理、grounded QA 和中文解释。Loss 只计算 assistant token 的交叉熵。是否进入 RL 不能只看 loss，而要在冻结 suite 上重复采样，检查格式有效率、工具行为、pass@k、失败结构和 group 是否产生可学习方差。

L_SFT = - Σ_t m_t · log pθ(y_t | x, y<t) / Σ_t m_t
m_t = 1 仅对 assistant action / final answer token 生效

4B 固定配方

Qwen3.5-4B、BF16、LoRA r/α=16、o_proj/gate_proj/up_proj/down_proj、gradient checkpointing、2 epochs、Adam、cosine LR 2e-5。

2×2 对照

B0 Base；B1 SFT-only；B2 RL-only；B3 SFT→RL。B1/B3 共享同一 SFT checkpoint，RL 两支共享 task 顺序、Reward、环境和 rollout 预算。

Readiness 四种决策
继续 SFT：协议/格式错误主导且新增示范仍有边际收益。
先修评测：parser、verifier 或输入视图不一致。
进入 RL：基本协议稳定、存在 mixed outcomes 和可学习搜索/恢复策略。
已饱和：多次扩数据和训练不再改善冻结能力/成本曲线。
为什么保留 RL-only？
它量化 Base 能否直接通过环境反馈学会策略，并检验 SFT 是否主要提供 policy initialization。若只比较 SFT 与 SFT→RL，就无法区分 RL 本身的增益与 SFT 初始化的协同作用。
实验边界： 4B 正式 SFT 结果尚未完成，9B 当前只完成模型、数据和脚本准备。不得把 2B Pilot 外推为 4B/9B 结论。

模型生成 Tool Call 后，系统到底做了什么？

A · 真实实现

模型只看到当前任务公开的 schema。Hermes 用 Qwen3 parser 解析调用，经临时异步 handler 交给 Frozen Environment；环境校验工具、参数、Search→Read 状态和预算，返回确定性 observation。Gold 调用或证据不在模型输入中，只由 Reward 侧核验。

knowledge_search(query) → discovered source_ids
knowledge_read(source_id) → only if source_id was discovered in this rollout
unknown / wrong args / direct read / over budget → deterministic error + trace

Parser parity

tool_call_parser=qwen3_coder、HF chat template、统一 tool serialization，避免 policy 与环境解释不同。

Task scope

每题只注册允许工具，结束立即注销；不能访问 shell、文件系统、网络、凭证或生产服务。

双层停止

6 turns / 6 calls 的数据合同，加上重复失败、同工具失败和 no-progress guardrail。

为什么不能只在 prompt 中写“先搜后读”？
RL 会优化 Reward，而不是遵守意图。若环境允许猜 source ID 直接读，策略可能找到 shortcut。约束必须进入状态机，并把违规写入 trace 与 Reward hard gate。
代码： training/rl/frozen_environment.py、training/rl/hermes_workflow.py、training/rl/budget_contract.py。ToolACE 连续 assistant/tool rounds 会全部保留，中间 tool call 不会被当作 final。

GRPO 的学习信号从哪里来？

A · 真实 Gate/Smoke

同一任务采样 4 条轨迹，用组内 Reward 均值和标准差构造相对 advantage。高于组平均的行为被增强，低于平均的被抑制；若四条 Reward 相同，zero-variance group 几乎没有相对信号。因此要同时看平均 Reward、组内方差、best–worst gap 和有效 group 数。

A_i = (r_i - mean(r_G)) / (std(r_G) + ε)
ratio_t = exp(log πθ(a_t|s_t) - log πold(a_t|s_t))
L_clip = min(ratio_t A_t, clip(ratio_t, 1-ε, 1+ε) A_t)

Group

n_samples=4，drop_incomplete_group=true；缺样本时拒绝训练，不改变 advantage 语义。

Stability

clip 0.2、KL control 0.02、token-level ratio rejection；无 EOS 轨迹把 outcome reward 清零。

Stage

Gate 1 step / 32 trajectories；Smoke 10 / 320；Pilot 25 / 800。分别验证链路、分布和短趋势。

GRPO 与 PPO 的主要区别？
当前配方不训练 value critic，而用同 prompt 多样本的相对 Reward 估计 advantage；policy update 仍保留 PPO 风格 ratio、clip、KL 和 off-policy 处理。不能简单说“GRPO 完全不是 PPO”。
什么是健康探索，什么是失控？
短期成功率下降但 entropy、KL、长度、ratio 和 holdout 未越界，且 group 有方差，可能是健康探索；若 Reward 与独立 eval 背离、entropy 快速坍塌、ratio tail/clip 激增或输出模式化，则应暂停并做 LR/KL/reward/data 对照。
v2 Gate： direct-gate-seed-7401-20260826_155650，Git 2bbc37b，证据包完整。历史边界：旧 v1 10-step Smoke 为 80 tasks / 320 rollouts，Reward mean 0.1292、std 0.5035、zero-variance 0.2875；它只证明旧链路有信号，不进入 v2 能力对照。

Reward 怎样既可学习，又不鼓励走捷径？

A · Reward v2B · Hacking 待受控

总分拆成任务成功、证据、引用、工具质量和效率，每项单独落盘。明确的协议/环境错误使用 hard gate；空回答、缺必要引用、完全不调工具最多为 0。Function Calling 把调用正确性与最终答案按 70/30 合成，修复“调对工具但不回答也能高分”的 shortcut。

R = .40 task_success + .25 evidence + .15 citation
  + .15 tool_quality + .05 efficiency - violations

Function task_success = .70 call_correctness + .30 answer_quality

Hard gate

非法引用、source 不存在、工具预算耗尽、未知工具、不支持 capability → Reward = -1。

四层防线

Oracle 隔离 → 环境状态机 → 多分量 Reward → 固定独立 Eval。任何单层都不足以防 hacking。

Outcome 与 Process Reward 如何取舍？
当前优先可验证 outcome；证据、引用和工具质量提供轻量 process constraint。不对不可可靠验证的自然语言 CoT 强行逐步打分，避免把 judge 偏差变成训练目标。
如何识别 Reward hacking？
检查 component domination、Reward 与 strict eval 背离、异常短答/长答、无工具高分、parser FP/FN、高分错误轨迹和 per-family 回归。自然训练未出现时，从健康 checkpoint 做短时、单变量、明确标记的 CONTROLLED_FAULT，再恢复 Reward 并在同一 suite 回归。
局限： QASPER 的 token-F1/字符串匹配可能低估语义等价回答；当前没有大规模人工校准的 learned RM。代码： training/rl/reward_v2.py、Reward 单测与每 trial 的 reward-v2.jsonl。

为什么平均 Reward 不能代表 Agent 变好？

A · Base Eval32 v2

Strict

Pass@4

Consistent@4

双卡 Agentic RL 的显存与故障边界怎样控制？

A · 双 H100 实测C · 扩展边界

GPU0 放 AReaL actor/reference 的 FSDP 训练，GPU1 放 SGLang rollout。LoRA、BF16、gradient checkpointing 和 4096-token microbatch 控制峰值。启动前每卡至少 76,000 MiB 空闲；运行超过 68,000 MiB 或出现外来进程时，仅终止本 trial 的 PGID。

GPU0

Actor + reference，参数、optimizer、gradient、activation、FSDP buffer 与 CUDA reserved memory。

GPU1

SGLang policy rollout、KV cache、并发请求与 LoRA hot load。

Guard

5 秒采样、显存阈值、foreign PID 检测、仅清理自己进程树，失败 run 也保留 exit reason。

显存为什么不能只按权重大小估算？
还包括梯度、optimizer state、activation、reference forward、通信 buffer、KV cache、CUDA allocator reserved memory 和临时 kernel workspace。不同阶段峰值不同，必须用 Gate 实测并保留分 GPU 时间线。
为什么不是 VeRL/TRL/Unsloth？
当前选择 AReaL 是因为它已提供 AgentWorkflow、解耦 rollout/update、FSDP 与 SGLang 接线；Hermes 提供成熟工具 loop。未对所有框架做同硬件 benchmark，因此只能陈述需求匹配和已验证链路，不能宣称全局最优。
边界： 双 H100 的 4B Gate/Smoke/Eval 只能证明该配方可运行；不证明 9B、百卡扩展或其他 GPU 有同样吞吐和稳定性。

RAG、Web、Memory 与 Agent Policy 是什么关系？

A · 离线 RAGC · RL 环境边界

StudyHub 确实在隔离的离线项目中实现过 BM25、BGE-M3/Qwen embedding、FAISS、Hybrid/RRF 和 cross-encoder rerank；当前 RL Frozen Environment 为控制变量使用简化词法检索。Retriever 解决“候选是否相关”，Agent RL 解决“何时搜、搜什么、读什么、是否继续和怎样引用”，二者不能混称。

层当前真实状态不应宣称
离线 RAG 实验BM25 / Dense / FAISS / Hybrid / RRF / Reranker 已实现并比较已经成为线上搜索
RL Frozen Search冻结 corpus + 确定性词法 search/read就是 BM25 或 BGE-M3
Web Adapter训练方案中按冻结环境设计已进行生产联网 RL
Memory训练主线暂时关闭，待独立消融已训练跨用户长期记忆
为什么 Pilot 不临时换 Hybrid Retriever？
同时改变 policy 与 retriever，就无法归因提升来自训练还是召回器。先固定环境比较 B0/B1/B2/B3，再将 sparse/dense/fusion/rerank 作为独立环境变量做 ablation。
Search-R1 借鉴了什么？
借鉴模型自主提出 search query、观察结果并继续推理的多轮策略研究问题；当前实际 harness 是 Hermes、trainer 是 AReaL、环境是 StudyHub FrozenTaskEnvironment，不能说原样复现并训练 Search-R1。
代码： ai_platform/rag_experiments/ 与 training/rl/frozen_environment.py。权限过滤必须在候选返回前 fail closed，不能依赖 LLM 最后自行隐藏付费资料。

为什么先做 GRPO，而不是把所有算法都跑一遍？

C · 选型理解D · 未实跑算法

当前最需要验证的是“冻结工具环境能否给 4B policy 提供稳定的相对信号”。GRPO 不需要 learned critic，适合有可验证 outcome、同题多轨迹和较高 rollout 成本的场景。其他算法只在对应症状出现、且能保持公平对照时进入，不为凑题面消耗训练预算。

算法核心变化何时考虑当前等级
PPOActor/Critic/Reference，GAE 与 clipped objective需要 learned value baseline，且资源允许C/D
GRPO同 prompt group-relative advantage可验证任务、多样 rollout、无 criticA
DAPO非对称 clip、动态采样/batch、overlong shapingzero-variance、长度和采样效率成为主瓶颈D
OPDstudent on-policy token + teacher logprob / reverse KL有合格 teacher，需保能力并纠正探索D
KDRL环境 Reward 与 distillation loss 联合RL 成功但通用能力遗忘D
DPO/KTO/IPO离线 preference objective有可靠偏好对，但不需要实时环境交互D
KL 与交叉熵 / MLE 有何关系？
MLE 最小化数据分布到模型的交叉熵，等价于忽略常数后的 forward KL；RL 中常用相对 reference policy 的 KL 作为 trust-region 约束。Reverse/forward KL 的 mode-seeking/coverage 性质不同；k1/k3 是 KL estimator 的数值取舍，不应与 KL 方向混为一谈。
诚实边界： 当前正式主线是 AReaL 的 PPO/GRPO 配方。DAPO、OPD、KDRL、GSPO、Dr.GRPO、CISPO、SAPO、DPPO、MaxRL、SimKO 等未在本项目形成 A/B 级结果。

哪些话现在不能说？

事实边界

Unsupported claims · 当前禁止外推

  • 不能宣称 4B SFT、Direct RL 或 SFT→RL 已提升 Eval32，直到 checkpoint 与成对评测完成。
  • 不能用训练 Reward 上升替代 strict success、pass@4、consistent@4 或 sealed test。
  • 不能宣称 9B 优于 4B；9B 当前只有模型、数据、脚本和配方准备。
  • 不能把 Frozen Search 称作 BM25/Dense/Hybrid，也不能说离线 RAG 已上线。
  • 不能说 Search-R1 已被原样复现训练；当前借鉴的是研究问题与多轮检索思想。
  • 不能把 Reward v2 称为大规模人工校准的教育 Reward Model。
  • 不能把 fixture/offline RL 外推为生产网络、数据库、权限和真实用户 online RL 安全性。
  • 不能把受控 entropy collapse/reward hacking 描述为自然生产事故。
怎样把限制说得专业，而不是显得“没做完”？
先说证据支持的范围，再说明剩余变量和下一步验证。例如：“双 H100 上 4B 的 Hermes→SGLang→Frozen Env→Reward→LoRA 链路已经完成真实 Gate；这证明配方可运行，但 9B scale effect 和业务收益仍需同协议复现。”

证据来源。 StudyHub 仓库代码、Git commit、Git-ignored 本地 artifacts、模型/数据 manifests，以及 artifacts/interview-goal-source/ 中已校验的 Goal Pack。原压缩包在双 manifest 校验后删除。

当前基线。 Base-4B Eval32 v2 两次固定 seed 运行获得 128/128 精确行为复现；Eval32 是开发评测，不是 sealed final benchmark。后续结果必须按 B0/B1/B2/B3 同协议追加。
