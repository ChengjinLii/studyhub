## 当前主线

产品方向已调整为独立知识库、RAG 与 Agent，详见 [独立产品设计](specs/2026-10-16-independent-knowledge-design.md)。不以主站 API、账户、订单、MySQL 或生产对象存储作为开发前提。

本轮已建立文档入库、PDF/OCR、版本化来源、Parent-Child 分层索引、混合检索、固定 RAG、知识 Agent 与增量 Wiki 的独立入口。现有执行器与历史测试保留，旧业务工具不进入新入口。实现对照见 [源码对照与验收](specs/2026-10-16-rag-wiki-guard-alignment.md)。

新的实施顺序：

1. 核对文本来源定位、公式/代码/表格保真、失败恢复与知识范围隔离。
2. 在固定公开或授权语料上评测解析质量、正文检索、混合检索及重排。
3. 比较同模型下的固定 RAG 与多步 Agent，建立片段级支持事实和不可回答评测。
4. 在已有 PDF/OCR 与增量 Wiki 基础上，推进持久化检索、隔离解析进程、异步任务及独立 API/UI。
5. 稳定工具协议和数据集后再设计 SFT/RL。

增量 Wiki 已提供独立命令与可选召回通道；知识图谱、浏览器和沙箱仍不作为默认依赖。以下保留的架构比较路线属于历史研究记录，不再按原网站资料业务假设继续扩充。

## 研究方向

| 方向 | 工作内容 | 评测指标 |
| --- | --- | --- |
| 故障注入与恢复 | 注入工具错误、超时和脏数据，评估再训练恢复能力 | 故障下的任务成功率 |
| 回答自检 | 检查引用来源并衡量纠正策略效果 | 引用精确率、幻觉率 |
| 上下文工程 | 工具结果压缩、摘要与长轨迹记忆管理 | 长任务成功率、任务 token 用量 |
| 模型级联 | 先比较 4B→9B，后续再考虑 27B 对照 | 同等准确率下的成本与延迟 |
| 可验证奖励 | 基于环境状态构造奖励并开展 GRPO | 相对 SFT 的配对增益与置信区间 |

执行循环保持精简的 ReAct 结构。复杂度的增加必须在固定任务、统一契约和配对统计下体现收益。

## 技术决策

### 执行框架

运行框架保持自研的小型 Python 循环，统一使用项目的渲染契约。[pi](https://github.com/badlogic/pi-mono) 提供精简执行框架的设计参考，不作为代码来源。工具结果采用模型可见 `payload` 与评测专用 `details` 分离的形式。

### 训练框架

训练阶段通过小规模验证比较 SkyRL、verl AgentLoop 与 Verifiers，检查以下条件：

- 使用本项目渲染器，保持训练与运行的聊天模板一致。
- 适配共享的两张 H100，资源安排服从实时可用显存。
- 推理引擎支持 Qwen3.5 的混合 GDN 架构。
- 支持 LoRA 与任务轨迹数据。

## 执行顺序

1. 建立故障注入、任务模型、确定性判分器、对抗校准集与 oracle。
2. 在 Dev 完成调试与架构比较，封存 Test 并登记曝光。
3. 生成可复现的结果表、配对统计和成本分析，再选择 SFT / RL 方案。
