Q01

为什么 StudyHub 需要 Agent，而不是一次普通 RAG？

项目成立性 · Agentic RL vs reasoning RL

A_REAL
普通 RAG 通常是固定的检索再生成；StudyHub 任务要求模型根据不完整 Observation 决定搜不搜、Query 怎么改、读哪个 source、何时停止和如何恢复工具失败。动作会改变后续状态，因此训练对象是多轮策略，而不只是最终答案推理。
60 秒机制

普通 reasoning RL 的环境常退化为 prompt→answer→verifier；Agentic RL 的状态包含对话、工具结果、预算和历史动作，动作包括 Tool Call、参数、继续/停止与 Final。Reward 同时检查任务结果、工具合法性、证据和引用。Tool observation 不参与 assistant loss，只有模型动作 token 被优化。

3 分钟项目证据与追问

当前链路是 AReaL→SGLang→Hermes→FrozenTaskEnvironment→Reward v2→GRPO LoRA update。两条 25-step Pilot 各产生 800 条 rollout，并记录 policy version、工具轨迹、Reward 分量和强制收尾。可继续追问：为什么环境冻结、哪些动作 mask、如何避免 Oracle 泄漏、为什么没有直接连生产 StudyHub。

证据：training/rl/hermes_workflow.py · training/rl/frozen_environment.py · 两个 Pilot evidence bundle。
Q02

Hermes、AReaL、SGLang 和 StudyHub 各自负责什么？

框架职责 · 最小修改原则

A_REAL
Hermes 保留原生 Agent loop 和 Tool Call 编排；SGLang 提供当前策略的高吞吐推理；AReaL 管 rollout、logprob、group advantage 和 LoRA update；StudyHub 只做薄适配：任务工具、冻结环境、预算、安全、Reward 和证据落盘。
60 秒机制

模型调用工具后，Hermes 将 Observation 追加回消息状态；Frozen Environment 实际执行 deterministic fixture 或 corpus Search/Read；Reward 不进入 policy context；AReaL 收到完整 trajectory 后形成 group-relative learning signal。这样没有重写 Hermes 核心，也没有让训练逻辑侵入网站后端。

3 分钟项目证据与追问

曾经出现 system prompt 被 Hermes 的 build path 与 ephemeral path 重复注入。修复不是删掉 Hermes，而是清理重复入口；1160/1160 重复记录在修复后变为 118/118 恰好一次。这说明“薄适配”仍需做 input parity 审计。可追问框架选型：TRL 更适合单机简单训练，AReaL 提供 actor/rollout 分离；SGLang 和 vLLM 都可做服务，这里选择与 pinned AReaL 接线匹配的 SGLang。

证据：Duplicate Prompt Incident · integrations/hermes/。
Q03

SFT 和 RL 分别解决什么？什么时候该进入 RL？

行为冷启动 · 探索策略 · Readiness

A_REAL
SFT 用专家示范建立格式、Tool JSON、证据回答和中文解释的行为先验；RL 不再模仿固定轨迹，而是在环境里探索 Search/Read/Call/Stop 策略。只有协议基本稳定、环境可复现、Reward 可验证，并且同一 prompt 的多次 rollout 有 mixed outcomes 时，扩大 RL 才有意义。
60 秒机制

格式错误和基础能力缺失优先补 SFT；“存在多条合理路径、需要错误恢复、当前策略不是最优”才是 RL 的价值区。Readiness 要看 pass@k、all-fail/all-success、zero variance、失败类型、成本和 verifier 可靠性，不以 SFT loss 单点决定。

3 分钟项目证据与追问

项目用 B0/B1/B2/B3 做 2×2。SFT loss 从 0.57391 降到 0.56247，但 Eval32 的 SFT strict 只比 Base 高 1.563 pp，CI 跨 0；SFT→RL 也没有额外增益。因此当前判断不是“RL 成功”，而是链路已验证、Reward/任务仍需修。可追问为什么保留 RL-only、如何计算 interaction、为什么 9B 暂停。

证据：4B 2×2 报告。
Q04

五个开放数据集怎样分工？RL 数据为什么不是答案轨迹？

数据构造 · Task/Environment/Verifier

A_REAL
ToolACE 与 Hermes FC 教工具协议，2Wiki 教给定证据下的多跳组合，QASPER 教 grounded QA，COIG 教中文解释。做 RL 时隐藏专家动作和 Gold，只保留任务；把工具、Wikipedia context 或论文变成可交互环境，Gold 只给 verifier。
60 秒机制

SFT 的目标是最大似然模仿，因此可见正确 assistant trajectory；RL 的目标是让当前策略自己 rollout，所以输入若包含 expected calls、supporting facts 或 gold source，就变成答案泄漏。COIG 没有天然 Agent 环境，因此进入 SFT，不作为第一阶段 GRPO 主数据。

3 分钟项目证据与追问

SFT 为 3,000 条，来源比例 300/300/900/600/900；RL 为 ToolACE 400、Hermes 400、2Wiki 1,000、QASPER 600，共 2,400。构建器审计公开 task 不含 Oracle 字段，并检查 SFT/RL lineage overlap=0。可追问数据授权、revision/hash、group split、近重复和为何条数不等于“数据够”。

证据：datasets/processed/*/manifest.json · scripts/data/audit_open_rl_tasks.py。
Q05

怎样防止 SFT/RL/Eval 泄漏？

Oracle isolation · Group split · Input parity

A_REAL
不只按行随机切分，而是按 paper、source、tool template group 隔离；SFT 与 RL 检查 source/group overlap；RL public task 与 verifier 分文件、分 hash；Gold answer、expected calls 和 gold evidence 永远不进入 policy-visible context。
60 秒机制

exact 去重只能挡完全重复，不能挡同一论文不同问题、同一工具模板改写和共享 supporting facts。项目把 group lineage 作为最小隔离单位；环境和 verifier hash 被审计；Eval 使用固定 validation task，仍明确不是 sealed final test。

3 分钟项目证据与追问

2Wiki/QASPER 的 Gold evidence 只给 verifier；Function Calling 的 expected call 只用于 fixture 和评分。审计要求 allowed tools、gold source 存在、fixture 覆盖，以及公开字段中不出现 expected_answers、supporting_facts 等。可追问 answer-conditioned CoT：若 teacher 看过 Gold，必须记录可见输入，不能冒充部署时自然推理。

证据：RL dataset audit · manifest hashes · Eval32 protocol caveat。
Q06

4B SFT 的 Loss、LoRA 和显存配置是什么？

Assistant-only CE · Low-memory recipe

A_REAL
使用 assistant-only token cross entropy，system/user/tool observation 不计 loss；Qwen3.5-4B 以 BF16、LoRA r/α=16 训练，目标模块为 o/gate/up/down，2 epochs、Adam、cosine 2e-5，318 次更新，GPU 峰值 38,113 MiB。
60 秒机制

mask 的目的是学习模型动作而不是复述输入；LoRA 降低可训练参数、优化器状态和保存成本，gradient checkpointing 用计算换 activation 内存。目标模块同时用于 SFT 和 GRPO，保证 2×2 内部公平。

3 分钟项目证据与追问

3,000 条数据拆为 2,550/300/150；assistant token 占比 18.87%，p95 长度 1,098。Epoch2 val loss=0.56247，比 Epoch1 相对下降约 1.99%。可追问为什么不是 all-linear：当前四模块配方经过 SGLang hot-load Gate，先固定为 controlled-v1 recipe，尚未做 capacity ablation。

证据：SFT trial run-seed-6209-20260826_234708 · COMPLETE。
Q07

GRPO 与 PPO 的核心差别是什么？为什么选 GRPO？

Group-relative advantage · 无显式 Critic

A_REAL
PPO 通常用 Value/Critic 估计 advantage；GRPO 对同一 prompt 采样一组轨迹，用组内 Reward 标准化形成相对 advantage，省掉独立 Critic。StudyHub 的工具任务可自动验证且能为同题生成多路径，双卡下 GRPO 更适合作为起点。
60 秒机制

近似写成 Aᵢ=(rᵢ−mean(r))/std(r)。若同组全成功或全失败，std≈0，就没有排序信号；因此必须记录完整 group、group std 和 zero-variance rate。KL/ratio/clip 仍用于限制策略漂移，GRPO 不是“没有 PPO 机制”。

3 分钟项目证据与追问

两条 Pilot 都是 group size 4、200 groups，drop incomplete group。SFT→RL zero variance=36.5%，Search family=64.52%，说明当前最该修 difficulty/reward，而不是先加步数。可追问为何不用 PPO：当前没有可信过程级 value target，Critic 会增加显存与工程复杂度；长轨迹 credit assignment 成为瓶颈后才值得比较。

证据：metrics/reward-groups.json · training/rl/。
Q08

Agent Reward 怎样设计，为什么不能只看总分？

Outcome / Evidence / Citation / Tool / Hard gate

A_REAL
Reward v2 把任务结果、答案、证据、引用、工具质量和效率分开记录；unknown tool、invalid citation、空 Final 等关键错误触发 hard gate。总 Reward 只做训练与诊断，模型比较使用独立 strict protocol，避免优化 Reward shortcut。
60 秒机制

Function Calling 的 task success 由 70% call correctness + 30% final answer 组成；Search/Grounding 同时检查 Gold answer/evidence/citation。辅助格式奖励不能压过主任务结果，hard gate 用于不可接受行为，不应无限堆 soft penalty。

3 分钟项目证据与追问

SFT→RL Search family task_success=96.84%，但 citation component=-0.851，最终 Reward 接近 0；这揭示答案 verifier 偏易、引用没学会。若只看 task_success 会误判。可追问 learned RM：本项目没有训练 Reward Model，开放主观任务暂不进入主要 RL；LLM judge 只属于未来校准边界。

证据：training/rl/reward_v2.py · metrics/reward-groups.json。
Q09

讲一个 Reward hacking / shortcut 的项目案例。

受控回归，不冒充自然事故

B_CONTROLLED
旧 Function Calling 设计可能让模型正确调用工具后不回答仍拿高分，因为 answer score 没进入 task success。我构造“正确 call + 空 Final”回归样本，修成 70% call + 30% answer，并让空答案 hard fail；测试要求总分不为正且记录违规。
60 秒机制

这是项目内受控漏洞测试，不是正式 Pilot 中观察到模型大规模利用。它的价值是证明 Reward 的可利用面：模型优化的是数值目标，不是设计者意图。修复后同时用独立 strict evaluator 检查，避免 Reward 与 Eval 共用同一漏洞。

3 分钟项目证据与追问

旧公式按 call/tool/evidence/citation 可接近 0.8，空答案只软扣；新代码将 answer_quality 显式合入 function task_success，并在 empty_final_answer 触发封顶。可追问如何发现真实 hacking：看 Reward 上升但 strict/holdout 下降、典型轨迹、component 分布、parser FP/FN 和 counterfactual verifier。

证据：受控 Reward Shortcut 案例 · 单元测试。
Q10

为什么 Agent 评测不能只看平均 Reward？

Strict success · Pass@4 · Consistent@4 · CI

A_REAL
Reward 是训练目标，可能被权重和 parser 漏洞影响；Agent 还具有采样方差。项目用 strict rollout success 衡量单次可靠性，用 pass@4 衡量至少一条路径成功，用 consistent@4 衡量四次都成功，再按 task 配对 bootstrap 报告 CI。
60 秒机制

32 tasks 每题 4 rollout；组不满 4 直接 fail closed。Strict 不以总分阈值判断，而是要求 nonempty final、无 hard gate/violation、tool quality=1；Function 还需正确 call 与 answer，Search 还需 answer/evidence/citation 全部正确。

3 分钟项目证据与追问

Direct RL pass@4 从 Base 的 9.375% 到 15.625%，但 strict 仅 +1.563 pp、consistent 不变，且 CI 包含 0。SFT→RL 128/128 精确重放。可追问为什么不是 sealed final：Eval32 用 hidden verifier 但参与开发决策，仍可能被反复观察；最终结论需独立 holdout。

证据：scripts/train/evaluate_dev_rollouts.py · factorial bootstrap 输出。
Q11

这次发生熵崩塌了吗？如何判断与处理？

负证据也要诚实

A_NEGATIVE
没有。Direct RL entropy mean=0.334，SFT→RL=0.410，末段没有向 0 单调塌缩，梯度有限、KL 有界。真实观察到的是 Reward 末段下降和 zero-variance 偏高，不能把它改名为熵崩塌。
60 秒机制

熵下降本身不一定坏；要联合看输出多样性、group variance、KL、ratio/clip、长度和 holdout。如果 entropy 快速趋零且多样性、pass@k 同时下降，才考虑降低 LR、提高 KL/entropy regularization、增加采样温度或调整难度混合。

3 分钟项目证据与追问

Goal Pack 允许自然未发生时做受控 fault，但不设事故配额。当前训练成本与信息增益不支持人为制造一条假的“项目崩塌”；因此证据级别是 A 级“未观察到”加 D/C 级机制理解，不说“我解决过熵崩塌”。

证据：两个 Pilot trainer metrics；SFT→RL entropy first5=0.4086、last5=0.4232。
Q12

Agent 长上下文怎么管理？讲一个真实故障。

动态 token 预算 · 强制收尾 · 压缩

A_REAL
静态数据都低于 4,096，但多轮 Search/Read 让真实 prompt 超限，9 个请求各重试 3 次失败。修复是在每次调用前用同 tokenizer 精确计数、为 Final 预留 768 tokens、阈值触发只读收尾，并仅对强制收尾关闭 thinking。
60 秒机制

上下文预算必须计算 system、tools、history、observations、final instruction 和 completion reserve；不能只审计原始 prompt。Observation 先裁剪/压缩，必要时丢弃最旧完整 exchange；无法安全收尾时 fail closed 并 hard gate。

3 分钟项目证据与追问

第一轮修复挡住 provider 500，但 finalization 仍以 thinking 开始，形成 3777+319=4096。第二轮只关闭 final thinking，Gate 的 5/5 强制收尾成功。正式 SFT→RL 仅 9/2863 interaction 触顶，135 forced final 全部 no-thinking。

证据：Context Budget Incident。
Q13

Tool Call 从模型输出到训练 Loss 经过什么？

Schema · Parser · Environment · Action mask

A_REAL
模型按 Qwen tool template 输出结构化 call；parser 解析函数名和参数；Hermes 调 Frozen Environment；结果作为 tool Observation 回到下一轮；AReaL 只对 assistant 生成的 reasoning/action/final token 计算策略 loss，不训练 system/user/tool 文本。
60 秒机制

Environment 先验证 allowed tool、参数 schema、budget 和 Search→Read 顺序；错误返回 deterministic observation 并记 violation。Reward 再比较隐藏 expected call/evidence。Mask 错会让模型学复述 Observation，因此 chat template、serialization 和 mask parity 是训练前 Gate。

3 分钟项目证据与追问

ToolACE 构建器保留同一 user 后的全部工具轮次，避免把中间 call 当 Final；Function fixture 参数不匹配返回失败语义；Read 只能访问本 rollout 先 Search 发现的 source。可追问 MCP 与 Function Call：MCP 是能力发现/传输协议，Function Call 是模型行动表示，权限仍由宿主环境控制。

证据：training/rl/frozen_environment.py · ToolACE trajectory parser tests。
Q14

怎样证明一次 Agent RL 实验真的可复现？

Manifest · Hash · Replay · Lineage

A_REAL
保存 commit、resolved config、模型/数据/env/verifier hash、seed、GPU 监控、逐轨迹 policy version、Reward 分量、checkpoint lineage 和退出原因；再从 merged checkpoint 以 deterministic sampling 重跑同一 Eval，比较每题每条稳定字段。
60 秒机制

训练 seed 不能保证异步 rollout 字节级一致，因此 Claim 的复现重点是固定 Eval。Eval32 同时启用 deterministic sampling 与 deterministic inference，group 必须恰好 4；lr=0 的 eval 检查 LoRA before/after hash 不变。

3 分钟项目证据与追问

SFT→RL 两次 Eval 比较 32/32 task multiset、128/128 rollout stable fields，全相同；忽略字段只有时间、trial/group/rollout ID。合并 checkpoint 曾因 processor assets 缺失而失败，修复后才得到复现结果，说明“有权重文件”不等于可 reload。

证据：scripts/train/compare_eval_reproducibility.py · reproducibility JSON。
Q15

双卡训练怎样控制显存并避免影响别人？

Preflight · Foreign process · PGID cleanup

A_REAL
启动前要求每张目标卡空闲至少 76,000 MiB；运行中任一卡超过 68,000 MiB 或出现外来 GPU 进程就停止；只终止本实验 PGID。4B SFT 峰值 38,113 MiB，两条 RL 高卡峰值分别 66,782 和 65,214 MiB。
60 秒机制

Actor/update 与 SGLang rollout 服务显存角色不同，因此双卡占用不对称。Guard 同时记录 GPU memory/utilization、PID/PGID 和 trial secret；训练后清理 admin key 与子进程，避免误杀共享服务器任务。

3 分钟项目证据与追问

低显存手段包括 LoRA、BF16、gradient checkpointing、4096 sequence cap、microbatch 限制和 rollout/update 分卡。尚未做完整 TP/PP/FSDP scale study，也不把这次双卡经验外推为百卡稳定性。

证据：scripts/train/guarded_gpu_launch.py · evidence bundle system metrics。
Q16

4B 2×2 最终说明了什么？

Base / SFT / RL / SFT→RL

A_REAL
Direct RL 的 pass@4 点估计最高，为 15.625%，但四组 consistent@4 都是 3.125%；SFT、RL 和 interaction 的配对 95% CI 全部跨 0。结论是训练链路成立、增益结论不成立，当前应修任务与 Reward，而不是扩到 9B。
60 秒机制

SFT effect=B1−B0，Direct RL=B2−B0，RL after SFT=B3−B1，interaction=B3−B2−B1+B0。Strict interaction 点估计 -2.344 pp，CI [-8.594, 3.125]；Pass interaction -6.25 pp，CI [-25, 12.5]。

3 分钟项目证据与追问

SFT 降低训练 loss，但没显著提高 broad Eval；Direct RL 增加部分探索成功，但 hard gate 更高；SFT→RL 没表现出初始化协同。family 分析显示 grounding=0、Search citation 失败、Function invalid calls 高。可追问统计功效：32 tasks CI 宽，只能指导开发，不支持强结论。

证据：最终实验报告 · 10,000 次 paired bootstrap。
Q17

为什么没有继续做 DAPO、OPD、KDRL 或 PPO？

算法选择边界

D_BOUNDARY
当前瓶颈是 verifier/citation 与 zero-variance，不是 GRPO 优化器机制不够复杂。DAPO 适合处理 dynamic filtering、clip 与 overlong；OPD/KDRL 需要合格 teacher 的逐 action-token logprob；PPO 需要 Value/Critic。没有对应证据前堆算法只会混淆归因。
60 秒机制

DPO/KTO/IPO 是离线偏好优化，不直接替代在线工具环境探索；GSPO/Dr.GRPO 调整 sequence ratio 或 group 标准化偏差；这些都应由实际症状触发。普通 teacher chat 输出不能冒充 OPD 的 on-policy token-level teacher scoring。

3 分钟项目证据与追问

本项目只正式跑 GRPO。AReaL 上游是否支持其他算法与“项目已验证”是两回事。下一候选若 Search zero variance 仍高，可以先做 difficulty/dynamic filtering 小消融，再判断 DAPO；若长轨迹需要过程 credit，先建设可靠 PRM/step verifier，再考虑 PPO。

边界：当前为 D 级机制理解；没有 DAPO/OPD/KDRL/PPO 项目训练 artifact。
Q18

RAG、联网搜索和 Memory 在 Agent 中怎样隔离？

只读工具 · Evidence provenance · 用户边界

A_REAL
