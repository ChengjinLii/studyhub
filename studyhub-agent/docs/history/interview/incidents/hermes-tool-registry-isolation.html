Hermes 工具注册表隔离故障

完整 Regression 启动后发现冻结 Benchmark 工具与 Hermes 内置工具同名，立即停止受污染运行。

面试问题

如何保证 Agent 评测和 RL rollout 使用的是冻结工具，而不是宿主 Agent 的同名生产工具？

30 秒回答

Hermes 在进程级 registry 中已注册 web_search。旧适配器用新的 task toolset 注册同名工具时被拒绝，但随后只检查“这个名字是否存在”，因此误把内置项当作注册成功；清理阶段还会把内置项删除，使同一 worker 的后续任务随执行顺序变化。我在 160-task Regression 的首批日志看到明确 collision 后立即停止。修复使用 Hermes 自带的 snapshot/restore：显式覆盖、校验 active entry 与 handler 身份、episode 结束后按对象身份恢复旧项，并将同一逻辑用于 Benchmark、AReaL RL 和 Hermes bridge。

故障机制

Hermes built-in: web_search / toolset=web
        ↓
Benchmark register: web_search / task-local toolset
        ↓
registration rejected
        ↓
get_entry("web_search") != None   # 误判成功
        ↓
finally: deregister("web_search") # 又删除了内置项
        ↓
任务行为依赖 worker 内的历史顺序

为什么必须中止

风险影响
环境污染冻结 replay task 可能调用 Hermes 内置 Web 工具，Observation 不再可复现。
安全边界失效只允许 fixture 的离线评测可能意外触达外部工具实现。
顺序依赖第一个冲突任务与后续任务看到的 registry 状态不同。
RL 污染同一缺陷存在于 AReaL Hermes workflow，会破坏 rollout、Reward 与 logprob 对齐。

最小修复与验证

  1. 调用 snapshot_registration(name) 保存原对象。
  2. 用 override=True 安装 task-local handler。
  3. 同时验证 local slot、active entry、toolset 和 handler identity。
  4. 结束时调用 restore_registration(name, current, previous)，不再盲目 deregister。
  5. 集成测试故意以 frozen web_search 覆盖内置项，完成 tool loop 后确认原 toolset=web 恢复。
