Benchmark 能跑，
不等于测得准。

冻结 v1 通过了结构合同，却在正式 9B baseline 前暴露出测量有效性缺陷。

面试问题

为什么一个 35/35 结构检查全部通过的 Agent Benchmark，仍然不能直接用于训练前后能力结论？

30 秒回答

结构审计只能证明 schema、split、grader 和环境引用没有断裂，不能证明题目真的测到了命名能力。我复查 v1 后发现，“教师语义审查”没有调用模型或逐题人工判断，而是规则通过后自动给 5 分；Direct Answer 明示“不用工具”，Query Rewrite 没检查 query 是否变化，Permission Recovery 反而要求先撞 ACL，Deep Research 仍以关键词命中计分。因此保留 v1 的 hash 和运行证据，不篡改 lineage；新建 v2 重新设计量尺，再重跑 9B Base。

可复现缺陷

名义能力v1 实际判定风险
Teacher semantic QAreview_case() 做可达性规则检查；无 blocker 时固定赋 5 分。把 structural review 误称为 semantic review。
Tool abstention用户请求直接写“Without using tools / 不用调用工具”。测指令服从，不测自主工具相关性判断。
Query rewrite第一次固定失败；后续任何成功调用都可算 recovery。重复原 query 也可能通过。
Permission recovery强制出现 permission denial。惩罚主动规避明显私有资源的更安全策略。
Long horizon由 budget tier 直接标 10+。允许十步不代表成功必须依赖十步。
Deep researchrubric 最终仍走 substring concept matching。关键词罗列可能替代真实综合与论证。

上游方法如何约束修复

  • BFCL V4 的 relevance/irrelevance 划分用于构造不泄露策略的工具相关性任务。
  • tau-bench 的等价终态原则用于状态任务；不要求复刻单一 gold trajectory。
  • BrowseComp 的“难找、易验证”思想用于开放检索任务，但官方 evaluator 也必须审计后固定版本。
  • DeepResearchBench II 的原子化、可核验 rubric 用于多源综合；精确事实与开放语义维度分开评分。

处置

v1 保持冻结。它继续证明运行合同、Infra exclusion 和 Hermes 工具链，但不再承载正式能力结论。v2 将重建 source-group/template split，拆分 permission avoidance/recovery，检查 query change 与 evidence gain，报告 realized horizon，并加入自审/独立审查状态和 cluster-aware 统计。外部 Judge 的 401 不会被伪装成成功审查。
