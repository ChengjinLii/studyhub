# StudyHub Agent 2B v1.2 消融报告

日期：2026-07-31
结论：**两种 v1.2 续训方案均未通过门禁。停止三随机种子扩展，不启封最终
留出集，两个 v1.2 adapter 均不可上线。**

## 1. 实验范围

本轮从 v1.1 最佳诊断种子 `seed7703` 出发，先后做了两次低学习率续训：

1. 仅使用 900 条成对 hard negative 的定向续训。
2. 从未受第一次续训影响的原始 `seed7703` 重新出发，使用 1,500 条
   replay-balanced 混合数据续训。

全程只使用冻结的公开免费资料快照。未访问生产数据库、生产 API、网站后端、
付费资料或真实用户记忆。模型、数据、预测与评测产物均位于 Git 忽略目录。

教师记录保留用户指定的 `gpt-5.6-thinking` 标签，但当前运行环境不能独立验证
会话模型身份，因此样本仍属于 teacher-reviewed silver，而不是人工金标。

## 2. 第一次消融：仅训练难例

第一次消融使用 900 条 v1.2 数据：

| 类型 | 数量 |
|---|---:|
| 工具预算 `0/1` 成对边界 | 300 |
| 证据已就绪 / 尚未收集成对边界 | 360 |
| 工具观察注入后继续只读任务 | 150 |
| 直接回答、拒绝和空检索保留 | 90 |

训练完成且内部 token accuracy 为 `99.61%`，但原 300 条诊断集出现明显灾难性
遗忘：tool name 从 `83.67%` 降至 `67.00%`，合成契约从 `32.00%` 降至
`0%`，material ID 保真从 `94.55%` 降至 `82.73%`。模型形成了过强的
`read_pdf_evidence` 默认偏置，因此第一次消融被拒绝。

## 3. 第二次消融：回放平衡

第二次消融重新从原始 v1.1 `seed7703` 开始，数据构成为：

| 组件 | 数量 |
|---|---:|
| v1.2 成对难例 | 900 |
| v1.1 旧能力精确回放 | 300 |
| 新状态 / 措辞 / 工具边界别名 | 300 |
| 合计 | 1,500 |

300 条回放覆盖 inspect、memory、synthesis、search、direct answer、refusal 和
material ID 保真。300 条新别名覆盖：

- 100 条合成状态别名。
- 80 条 inspect / read 边界。
- 50 条当前用户 memory / PDF 边界。
- 40 条零预算收束措辞变体。
- 30 条权限拒绝措辞变体。

数据审计结果：

- split 为 `1350 train / 150 validation / 0 test`。
- 1,500 条记录无重复 query-target 对、无 material split 泄漏。
- 不含付费资料；新增别名与诊断集无精确 query、payload 或 target 重合。
- 最长 `938` tokens，无截断和空 target。
- 封存的 `final_holdout_v2` 未读取。

训练配置为 LoRA rank 16 / alpha 32 / dropout 0.05，学习率 `1e-5`，
1 epoch，BF16，单张 H100。训练正常完成：

| 指标 | 结果 |
|---|---:|
| Optimizer steps | 169 |
| Train loss | 0.1535 |
| Validation loss | 0.0311 |
| Validation token accuracy | 99.25% |
| 用时 | 829.6 s |

## 5. 失败归因

第二次消融修复了部分旧能力：

- `inspect_after_retrieval`：30/30 正确。
- `read_personal_memory`：25/25 正确。
- 工具观察注入：20/20 保持白名单只读动作。
- 工具必需场景的 Mode：100% 正确。

但关键流程仍不稳定：

- 25 个应合成上下文的场景中，23 个仍重复调用 `read_pdf_evidence`，只有 2 个
  调用 `synthesize_course_context`。训练别名带有 `executed/pages` 等强提示，
  诊断结构只有较简洁的 evidence status，模型没有学会结构缺省下的状态语义。
- 20 个零预算场景只有 12 个输出 final；5 个错误调用 `inspect_materials`，
  3 个 final 输出生成了损坏的 `chunk_id` JSON。
- 30 个权限拒绝场景有 1 个错误调用 `search_materials`。
- 直接回答场景虽然 20/20 选择 final，但有 2 个输出不满足完整 JSON 契约。

这不是 RL 问题。当前主要瓶颈仍是状态表达泛化、schema 解码稳定性和
SFT 任务冲突。

## 6. 门禁决策

1. 两个 v1.2 adapter 仅保留为失败实验产物，不标记生产候选。
2. `eligible_for_three_seed_expansion=false`，不训练 seed 3407 和 9109。
3. `final_holdout_v2` 保持 `sealed=true`、`evaluated=false`，没有评测回执。
4. 不进入 RL；继续 RL 会放大尚未稳定的路由和 JSON 契约问题。
5. 下一轮若继续，应先设计独立于当前 300 条诊断模板的状态机一致性测试，
   再用结构字段 dropout、状态规范化和受约束 JSON 解码做小规模消融。

机器可读的配置、SHA-256、指标和门禁结果位于：
